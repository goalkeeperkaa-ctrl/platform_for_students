# Запуск платформы в бой

Порядок в документе — это порядок действий. Часть 1 (база) обязательна,
без неё остальное не имеет смысла: демо-режим хранит данные в памяти и
теряет их при каждом перезапуске.

**Что нужно заранее**

- Node.js 20 LTS или новее
- PostgreSQL 14 или новее
- Домен с HTTPS (куки сессии ставятся с флагом `Secure` в production)
- Redis — если инстанс будет не один (см. часть 5, шаг 4)
- Доступ к API вашей CRM — не обязателен на старте, вакансии можно
  завести и синхронизацией позже

# Часть 1. База данных PostgreSQL

## Шаг 1. Убедиться, что сервер работает

**Windows.** PostgreSQL ставится службой. Проверьте, что она запущена:

```powershell
Get-Service *postgre*
```

Если в колонке `Status` не `Running`:

```powershell
Start-Service postgresql-x64-16
```

Имя службы зависит от версии — подставьте своё из вывода первой команды.

**Linux.**

```bash
sudo systemctl status postgresql
sudo systemctl start postgresql
```

Проверка, что порт слушается (обе системы):

```bash
psql --version
```

## Шаг 2. Создать отдельного пользователя и базу

Не используйте суперпользователя `postgres` для приложения: если утечёт
строка подключения, у злоумышленника будет доступ ко всем базам сервера,
а не к одной.

Зайдите в консоль под суперпользователем и заведите базу:

```sql
CREATE DATABASE fhr_students ENCODING 'UTF8';
```

`ENCODING 'UTF8'` обязателен: в базе лежат русские названия вузов,
компаний и специальностей.

Владельцем оставьте администратора, а не приложение. Роль приложения
заводится отдельной командой — пропишите в `.env` строку подключения
администратора и выполните:

```bash
npm run db:provision
```

Команда создаёт роль `fhr_app` со случайным паролем, выдаёт ей право
читать и писать строки — и **только его**. Создавать и удалять таблицы
она не может: это делают миграции, и ходят они отдельной строкой
`DIRECT_DATABASE_URL`. Обе строки команда сама запишет в `.env`.

Почему не сделать приложение владельцем базы, как советуют обычно:
владелец может удалить любую свою таблицу. Тогда SQL-инъекция в рантайме
всё ещё способна снести данные целиком, и защищает от этого только
внимательность в коде. Здесь же прав нет у самого подключения.

Пароль роли нигде не печатается — вывод команды попадает в историю
оболочки и в логи CI. Смотрите его в `.env`. Сменить: `npm run db:provision -- --rotate`.

## Шаг 3. Проверить, что подключение живое

```bash
psql -U fhr_app -h localhost -d fhr_students -c "SELECT current_database();"
```

Должно вывести `fhr_students`. Если ругается на пароль — вы либо ошиблись
при вводе, либо в `pg_hba.conf` для локальных подключений стоит метод,
который его не спрашивает.

## Шаг 4. Сгенерировать ключи приложения

```bash
npm run keys
```

Команда напечатает два значения:

- **`PII_ENCRYPTION_KEY`** — мастер-ключ шифрования персональных данных.
  Им зашифрованы ФИО, почта, телефоны и вся переписка. **Потеря ключа
  равносильна потере этих данных: расшифровать их будет нечем.** Смена
  ключа на работающей базе делает нечитаемым всё, что записано раньше.
  Держите его в секрет-менеджере, а не в репозитории.
- **`JWT_SECRET`** — подпись сессий. Смена немедленно разлогинивает всех.
  Это не страшно, но пользователей предупредите.

## Шаг 5. Заполнить `.env`

```bash
cp .env.example .env
```

**Именно `.env`, а не `.env.local`.** Next.js читает оба файла, но Prisma
CLI и скрипты (`db:push`, `db:seed`, `admin:create`) — только `.env`.
Если ключ шифрования окажется в разных файлах с разными значениями,
скрипты зашифруют данные одним ключом, а приложение попытается
расшифровать другим, и в кабинете работодателя вместо имён будет каша.

Заполните минимум:

```
DATABASE_URL="postgresql://fhr_app:пароль@localhost:5432/fhr_students?schema=public"
PII_ENCRYPTION_KEY="<из шага 4>"
JWT_SECRET="<из шага 4>"
```

Если в пароле есть `@`, `:`, `/`, `?`, `#` или `%` — их нужно закодировать
процентами, иначе строка подключения разберётся неправильно и Prisma
сообщит про неверные учётные данные при верном пароле. Проще не
угадывать, а выполнить:

```bash
npm run db:connect
```

Скрипт спросит пароль (ввод не отображается), проверит его, создаст базу,
если её нет, закодирует спецсимволы и впишет готовую строку в `.env`.

## Шаг 6. Создать схему

Для первого развёртывания на боевом сервере нужна миграция, а не `db:push`:
миграции версионируются и повторяемы, `db:push` просто приводит базу к
схеме и не оставляет истории.

Папка `prisma/migrations` уже есть в репозитории — базовая миграция
`0_init` описывает всю схему. Делать ничего не нужно, просто накатите:

```bash
npx prisma migrate deploy
```

Эта же команда выполняется при каждом последующем развёртывании и
применяет только то, чего в базе ещё нет.

Ходит она строкой `DIRECT_DATABASE_URL`, то есть правами администратора.
У роли приложения прав на изменение схемы нет — и это не мешает
развёртыванию, потому что миграции запускают отдельно от приложения.

**Не используйте `npm run db:push` на бою.** Он приводит базу к схеме
напрямую, не оставляя истории: откатить изменение будет нечем, а
несовпадение с кодом обнаружится не при развёртывании, а на живых людях.

Если база уже существует и создана через `db:push` (истории миграций
нет), её нужно один раз привести к общему порядку:

```bash
npx prisma migrate resolve --applied 0_init
```

Команда отмечает базовую миграцию как применённую, ничего не меняя в
данных. После этого `migrate deploy` работает как обычно.

## Шаг 7. Убедиться, что приложение видит базу

```bash
npm run dev
```

В логе **не должно** быть строки:

```
[store] DATABASE_URL не задан — включён демо-режим в памяти процесса.
```

Её отсутствие и означает, что работа идёт с PostgreSQL.

# Часть 2. Убрать демо

Демо устроено не одним рубильником, поэтому разберём по частям: что
отключается само, что нужно заменить руками и чего нельзя запускать.

## 2.1. Что отключается само, делать ничего не нужно

**Подсказка с демо-доступами на экране входа.** Показывается по условию
`isDemoMode()`, то есть только когда `DATABASE_URL` не задан. Как только
база подключена — исчезает. Файлы: `app/login/page.tsx`,
`components/screens/LoginForm.tsx`.

**Хранилище в памяти.** В production подмены не происходит вовсе: без
`DATABASE_URL` приложение падает на старте с внятной ошибкой, а не
переходит тихо в память. Молча потерять данные хуже, чем не запуститься.
Файл: `lib/db/index.ts`.

## 2.2. Что обязательно заменить руками

Это единственное, что реально утечёт на боевой сайт, если не тронуть.

**Витрина на главной странице.** Карточки вакансий, которые посетитель
листает на лендинге, берутся из демонстрационной выгрузки — «Кофейни
„Север“», «Metrika Digital» и остальные вымышленные компании. Они
показываются **всегда, в том числе в production**.

Файл: `lib/showcase.ts`, функции `showcaseVacancies()` и
`showcaseCompanies()`. Оба берут данные из `CRM_VACANCIES`
(`lib/db/seed-data.ts`).

Варианты:

1. Заменить содержимое `CRM_VACANCIES` на несколько реальных вакансий —
   быстро, витрина остаётся статической и открывается мгновенно.
2. Переписать `showcaseVacancies()` на чтение из базы (`store.vacancies
   .listActive()`) и добавить в `app/page.tsx` строку
   `export const revalidate = 300`. Витрина станет живой ценой того, что
   главная начнёт зависеть от базы.

**Цифры на лендинге.** «860+ студентов», «48 компаний-партнёров», «3 дня
до первого ответа», «71% доходят до собеседования» — правдоподобные, но
выдуманные. Файл: `components/screens/Landing.tsx`, компоненты `Metric`.
Замените настоящими или уберите блок.

## 2.3. Чего нельзя запускать на боевом сервере

```bash
npm run db:seed   # ← только для разработки
```

Эта команда создаёт: 14 вымышленных вакансий, 8 компаний,
демо-студентов, администратора `admin@fattakhov.ru` с **общеизвестным
паролем** и код доступа работодателя `SEVR-2026-DEMO`.

На бою вместо неё — часть 3.

## 2.4. Если хотите вычистить демо совсем

Не обязательно: в production оно и так не всплывает, а для локальной
разработки удобно. Но если решите — вот полный список:

| Файл | Что убрать |
|---|---|
| `lib/db/seed-data.ts` | `DEMO_CREDENTIALS`, `DEMO_STUDENT_PROFILE`, содержимое `CRM_VACANCIES` |
| `prisma/seed.ts` | весь файл |
| `lib/db/memory.ts` | весь файл (хранилище в памяти) |
| `lib/db/index.ts` | ветку с `createMemoryStore()` и функцию `isDemoMode()` |
| `app/login/page.tsx` | блок `demoHint` |
| `components/screens/LoginForm.tsx` | проп `demoHint` и его вывод |
| `tests/smoke.ts` | проверки завязаны на демо-данные — либо перепишите на боевые, либо удалите |
| `package.json` | скрипт `db:seed` |

После удаления `lib/db/memory.ts` перестанет работать `npm run dev` без
базы — это осознанный размен.

# Часть 3. Первое наполнение боевыми данными

## Шаг 1. Завести HR-менеджера

```bash
npm run admin:create -- hr@fattakhov.ru
```

Скрипт дважды спросит пароль (ввод скрыт) и проверит его теми же
правилами, что и пароль студента: не короче 8 символов, буквы и цифры.
Повторный запуск с той же почтой меняет пароль — это же и способ сброса,
если он потерян.

Без этого шага в панель HR-менеджера войти будет некому: регистрация
через интерфейс заводит только студентов.

## Шаг 2. Загрузить вакансии

Вакансии приходят синхронизацией из CRM агентства. В `.env`:

```
CRM_SYNC_URL="https://crm.fattakhov.ru/api/export/vacancies"
CRM_SYNC_TOKEN="<токен для Bearer-авторизации>"
```

Ожидаемый ответ — JSON вида `{ "vacancies": [ ... ] }`, где каждый
элемент соответствует контракту `CrmVacancyInput` из `lib/db/types.ts`:

```json
{
  "crmId": "CRM-1001",
  "companyName": "Название компании",
  "contactName": "Имя контактного лица",
  "contactEmail": "hr@company.ru",
  "crmClientId": "client-xxx",
  "title": "Название вакансии",
  "summary": "Короткое описание",
  "responsibilities": ["…"],
  "requirements": ["…"],
  "perks": ["…"],
  "salaryFrom": 3200,
  "salaryTo": 4200,
  "salaryPeriod": "MONTH | SHIFT | HOUR",
  "city": "Москва",
  "district": "Хамовники",
  "workFormat": "ONSITE | HYBRID | REMOTE",
  "employmentType": "PART_TIME | SHIFT | PROJECT | INTERNSHIP | FULL_TIME",
  "shiftDays": ["MON", "TUE"],
  "hoursPerWeek": 24,
  "tags": ["Без опыта"],
  "isHot": true,
  "isActive": true,
  "publishedAt": "2026-01-15T10:00:00.000Z"
}
```

Как это работает:

- **`crmId`** — ключ сопоставления. Вакансия с новым `crmId` создаётся,
  с известным — обновляется.
- **`crmClientId`** — ключ компании. Работодатель заводится
  автоматически при первой вакансии, повторно не дублируется.
- Вакансия, **пропавшая из выгрузки**, снимается с публикации, но не
  удаляется: на ней висят отклики.
- Каждый запуск, включая падения, пишется в таблицу `SyncRun` и виден в
  панели HR-менеджера.

Запуск — кнопка «Синхронизировать вакансии» в панели HR-менеджера.
Пока `CRM_SYNC_URL` пуст, кнопка загрузит демонстрационную выгрузку из
`lib/db/seed-data.ts` — на бою это не то, что нужно, поэтому либо задайте
URL, либо замените содержимое `CRM_VACANCIES` реальными вакансиями.

## Шаг 3. Выдать работодателям коды доступа

У работодателя нет регистрации: аккаунт создаётся синхронизацией, а войти
он может только по коду.

```bash
npm run employer:code -- "Название компании"
```

Или по идентификатору из CRM, с подписью и сроком:

```bash
npm run employer:code -- client-sever --label "Анна, управляющая" --days 90
```

Код печатается **один раз**. В базе лежит только его хеш — восстановить
исходную строку нельзя. Потерян — выпускайте новый; старый продолжит
работать, пока не истечёт.

Передавайте код тем каналом, который у вас принят для чувствительных
данных, — не в общий чат.

# Часть 4. Подключение к основному сайту

Платформа — самостоятельное Next.js-приложение со своей сессией. Есть два
способа поставить её рядом с основным сайтом.

## Вариант А. Поддомен — рекомендуемый

`students.fattakhov.ru`

**Шаг 1.** Заведите A/AAAA-запись поддомена на сервер с платформой.

**Шаг 2.** Выпустите сертификат (Let's Encrypt или ваш обычный способ).

**Шаг 3.** Настройте обратный прокси. Пример для nginx:

```nginx
server {
    listen 443 ssl http2;
    server_name students.fattakhov.ru;

    ssl_certificate     /etc/letsencrypt/live/students.fattakhov.ru/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/students.fattakhov.ru/privkey.pem;

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_http_version 1.1;

        # Реальный IP нужен лимитам запросов и журналу аудита:
        # без него все обращения выглядят как один клиент
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header Host $host;

        # Живой чат работает через Server-Sent Events. Без этих трёх
        # строк nginx буферизует поток, и сообщения приходят пачками
        # с задержкой в минуты либо не приходят вовсе.
        proxy_set_header Connection '';
        proxy_buffering off;
        proxy_read_timeout 3600s;
    }
}
```

**Шаг 4.** На основном сайте поставьте ссылки на `https://students.fattakhov.ru`:
в меню, на странице для соискателей, в подвале.

**Почему этот вариант.** Раздельные домены — раздельные сессии и куки:
взлом одного приложения не даёт доступ ко второму. Разворачивать и
обновлять платформу можно независимо от основного сайта.

## Вариант Б. Подпапка основного домена

`fattakhov.ru/students`

**Шаг 1.** В `next.config.mjs` добавьте:

```js
const nextConfig = {
  basePath: '/students',
  // остальное как было
};
```

**Шаг 2.** Прокси на основном домене:

```nginx
location /students/ {
    proxy_pass http://127.0.0.1:3000;
    # заголовки и настройки SSE — те же, что в варианте А
}
```

**Шаг 3.** Пересоберите приложение: `basePath` подставляется на сборке,
на лету не меняется.

**О чём помнить.** Оба приложения оказываются на одном домене, значит
делят пространство кук. Имя куки платформы — `fhr_session`; убедитесь,
что основной сайт не использует такое же. Обновление платформы придётся
согласовывать с прокси основного сайта.

## Единый вход — чего ждать не стоит

Общей авторизации между CRM и платформой нет. Это сделано намеренно:

- **студент** регистрируется сам, в CRM его нет;
- **работодатель** входит по коду, который выдаёт агентство, — паролей у
  него не заводится;
- **HR-менеджер** заводится командой из части 3.

Если единый вход нужен, это отдельная работа: OAuth-провайдер на стороне
CRM и приём токена на стороне платформы.

# Часть 5. Сборка и запуск

**Шаг 1.** Установить зависимости и собрать:

```bash
npm ci
npx prisma generate
npm run build
```

**Шаг 2.** Запустить:

```bash
npm run start
```

По умолчанию порт 3000, меняется через `PORT`.

**Шаг 3.** Держать процесс живым — systemd, PM2 или контейнер, что у вас
принято. Приложение не хранит состояния в процессе, перезапуск безопасен.

**Шаг 4. Если инстанс не один — Redis обязателен.**

```
REDIS_URL="redis://localhost:6379"
```

Без него ломаются две вещи:

- **Лимиты запросов** считаются в памяти каждого процесса, то есть
  фактический лимит умножается на число инстансов.
- **Живой чат.** Сообщение, отправленное через первый инстанс, не дойдёт
  до собеседника, подключённого ко второму: шина событий тоже
  процессная. Собеседник увидит его только после перезагрузки страницы.

Для одного инстанса Redis не нужен, приложение работает без него и
предупреждает об этом в логе один раз при старте.

**Шаг 5. Файлы пользователей.**

```
UPLOAD_DIR="/var/lib/fhr-students/uploads"
```

Сюда кладутся фотографии и резюме. Каталог должен переживать
перезапуск и развёртывание — во временной файловой системе контейнера
им не место. Файлы намеренно лежат вне `public/`: их раздаёт роут,
который на каждый запрос проверяет, кому они принадлежат.

# Часть 6. Проверка после развёртывания

Сначала машинная проверка базы:

```bash
npm run db:verify
```

Она не повторяет `smoke` — там проверяют, что всё работает. Здесь
проверяется то, что обычно находят уже после запуска: какими правами
ходит приложение, лежат ли персональные данные зашифрованными, есть ли
история миграций, не остались ли в базе демо-учётки, пароли которых
опубликованы в репозитории. Каждый провал объясняет, чем он обернётся.

Запускать её стоит и после каждого развёртывания: права в базе меняются
руками, а замечают это в последнюю очередь.

Дальше пройдите вручную:

1. Главная открывается, карточки на витрине — настоящие, не «Кофейни „Север“».
2. Регистрация студента проходит, письмо-подтверждение не требуется.
3. В ленте видны вакансии из CRM, свайп вправо создаёт отклик.
4. Работодатель входит по выданному коду и видит этот отклик.
5. Работодатель пишет сообщение — студент получает его **без
   перезагрузки страницы** (это проверка, что SSE проходит через прокси).
6. HR-менеджер входит, видит статистику и запускает синхронизацию.
7. На экране входа **нет** блока с демо-доступами.

**Про автоматические проверки.** В проекте есть `npm run smoke` — 61
сквозная проверка. **Не запускайте их против боевого сервера:** они
регистрируют пользователей, отправляют сообщения и меняют статусы,
то есть засоряют настоящие данные. Только против локального или
тестового стенда.

На стенде каждый прогон оставляет учётку `smoke-<время>@demo.ru`:
в демо-режиме такие исчезали при перезапуске, на базе остаются. Убрать:

```bash
npm run db:clean-test -- --apply
```

## Резервные копии

```bash
npm run db:backup -- --keep 30
```

Ставьте в расписание (планировщик задач или cron) — ежедневно, с
хранением 30 дней. Копию складывайте не на тот же диск, что и базу.

Две вещи, без которых расписание бесполезно:

**Копия без ключа не восстанавливает персональные данные.** ФИО, почты и
телефоны лежат в дампе шифротекстом, а `PII_ENCRYPTION_KEY` в базе нет —
в этом и смысл шифрования. Ключ храните в секрет-менеджере и берегите
отдельно от копий. Потеряете его — восстановите структуру и обезличенные
поля, но не людей.

**Копия, которую ни разу не восстанавливали, — это предположение.**
Раз в квартал разворачивайте свежую копию на отдельной базе и
сверяйте количество строк. Проверка занимает пару минут:

```bash
createdb fhr_restore_check
pg_restore -U postgres -d fhr_restore_check --no-owner --no-privileges backups/<файл>.dump
```

## Смена ключа шифрования

Если `PII_ENCRYPTION_KEY` придётся сменить, **простая замена значения
ломает базу молча**: слепой индекс начнёт считаться новым ключом, вход по
почте перестанет находить учётные записи и ответит «неверная почта или
пароль» при верном пароле, а ФИО и телефоны станут нечитаемыми.

Порядок такой: старый ключ кладёте в `PII_ENCRYPTION_KEY_OLD`, новый — в
`PII_ENCRYPTION_KEY`, и до запуска приложения перешифровываете данные:

```bash
npm run keys:rotate            # отчёт: сколько строк затронет
npm run keys:rotate -- --apply # перешифровать
```

Команду можно повторять: строки, уже переписанные, она пропускает.

# Часть 7. Что осталось незакрытым

Честный список — это не сделано, и на бою может понадобиться.

**Выдача кодов работодателям только из консоли.** В панели HR-менеджера
кнопки нет, каждый код выпускается командой на сервере. Для десятка
компаний терпимо, для сотни — нет.

**Нет смены пароля и восстановления доступа.** Ни у студента, ни у
HR-менеджера. Пароль администратора сбрасывается командой
`admin:create`, пароль студента — никак. Понадобится форма
восстановления через почту.

**Студент не узнаёт о новом сообщении, пока не откроет сайт.** Ни почты,
ни пуш-уведомлений. Работодатель написал — студент увидит при следующем
заходе. Для скорости отклика это главное узкое место.

**Ротация ключа шифрования не предусмотрена.** Смена
`PII_ENCRYPTION_KEY` делает нечитаемыми все ранее записанные данные.
Для ротации нужна версия ключа в префиксе шифротекста и процедура
перешифровки.

**Нет автоудаления персональных данных.** Согласие на обработку
фиксируется с версией, датой и IP, но срок хранения не ограничен и
данные не чистятся автоматически.

**Резервное копирование не настроено.** Дамп базы плюс каталог
`UPLOAD_DIR`, и обязательно проверка восстановления — бэкап, который
никогда не разворачивали, бэкапом не является.

**Переписку не видит никто, кроме двух сторон.** HR-менеджер видит
воронку и «кто в процессе», но не содержимое сообщений. Это осознанное
решение. Если агентству нужен доступ к переписке — это отдельная роль с
обязательным журналированием каждого просмотра.
